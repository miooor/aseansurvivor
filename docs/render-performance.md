# Bounded water rendering cost reduction

Part of [ticket #15](https://github.com/miooor/aseansurvivor/issues/15) and [spec #8](https://github.com/miooor/aseansurvivor/issues/8). The production change skips fully offscreen water surfaces, including their internal WebGL filters and tile-position updates. It does **not** resolve the crowded desktop frame-rate limitation. The full 15-second comparison was 12.13 FPS before and 11.60 FPS after; no performance PASS or frame-rate target is claimed.

## Evidence and attribution

Measurements were taken on 2026-11-15 UTC using native Safari 26.3.1 on the same Apple M1 MacBook Air, eight CPU cores, 8 GB RAM and macOS 26.3.1 as the [original slow sample](evidence/gameplay-upgrade/desktop-profile.json). The real game renderer/iframe was 1280×720. No explicit CPU/network throttling was configured. The parent closed its browser acceptance tabs and stopped builds/tests throughout the timing window. The worker's own game was the foreground Safari tab; the existing Astrocade tab was left alone. The focused fixture nests the existing combined fixture; its iframe may extend below the visible browser window, while the game renderer remains 1280×720. Before/after comparisons use this same nesting.

The existing dev runtime stages an active hunt with one enraged elite and 96 mixed owned enemies, all with 100,000 maximum HP (elite starts at 50,000), an invulnerable hero, normal AI, auto mode 3, full initial R, disabled ordinary spawns and E/F/R casts through actual skill controls. Forked Conduit, Undertow Thread and Monsoon Lens are acquired using the existing fixture's real event/reward buttons; equipment is never assigned directly. Counts remain 97 living enemies. This is the same staged scenario as the original profile, not natural progression or a balance trial.

The ranked hypotheses were off-camera water filter work, skill effects/combat labels, then dense AI/separation. A fixture-only pre-render switch changed only visibility of water wholly outside a 150-world-unit padded player view. The game, enemies, in-view effects, simulation and artwork were retained. Inspection of installed Phaser **4.2.1** inside the container confirmed that `CameraManager.getVisibleChildren` calls `GameObject.willRender`, which checks render flags/camera filtering without spatial bounds. Filtered objects enter `renderWebGLStep` before their internal capture/composition. Instrumentation counts initial render-step entries, not GPU timings or individual draw calls.

## Production behavior

`OpenWorld.update` retains all water objects and cached masks. Only water visibility is bounded by the union of the previous camera world view and the arriving player's view at the current zoom, expanded by 150 world units. The union accounts for `SurvivalScene` centering the camera after the world update and for teleports, world changes and zoom changes; padding covers camera shake and edge arrival. A transition may conservatively render extra water for one frame. Visible water animation uses absolute simulation time, so it resumes at the correct phase. Other terrain, bridges, collision/navigation, combat, saves, filters and mask artwork are unchanged. Raids and menus still hide all outdoor terrain.

The old fixture assumptions that every outdoor water object is always `visible` are intentionally superseded. Environment checks now require every surface to remain allocated and to become visible on arrival. Retry checks require all surfaces plus visible arrival water. All previous actual rounded-corner, outside-bank and body pixel assertions remain, with additional actual viewport-edge water/ground comparisons at both zooms. The edge approach chooses valid ground and camera bounds, then verifies the sample is within 60 screen pixels of an edge. Early expanded-fixture diagnostics are retained as `water-edge-fixture-diagnostic*.json`: the first proposed approach entered blocked Penang water, the next hit camera clamping, and the fixed first point of Kedah's west canal had no valid unclamped shore approach. These are staging failures, not ignored pixel assertions; the final fixture selects another interior body point when required.

## Repeatable checks

Start the repository's container development server and open `/tests/render-performance.html`. **Check water visibility** must pass. **Compare all-water control (5 seconds each)** temporarily reproduces the old all-visible behavior in the fixture, then hides only offscreen water; these switches are not production APIs. Use a quiet, foreground window and download the report. **Profile original crowd (15 seconds)** and **Profile ordinary scene (15 seconds)** record observations without a machine-dependent FPS pass threshold. Reload the complete harness after source changes to avoid a stale HMR runtime.

Open `/tests/water-mask.html`, select **Run water checks**, require PASS and download the JSON. It retains all 14 waters, both zooms, the original 84 pixel pairs, transitions and repeated six-world texture cycles, and adds 28 edge pixel pairs. `/tests/environment.html` retains terrain/weather/hero checks and adds water visits. Build, typecheck and focused lint use the existing container and locked dependencies. No host packages, dependencies, assets or production testing APIs were added.
